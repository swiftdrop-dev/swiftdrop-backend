# Webhook subscriptions: proposed contract

Status: production design draft. A separate local-only implementation now exists
in `webhooks_dev` with an opaque server-configured test merchant ID. Its Flyway
migration stores subscription configuration only; signing secrets and actual
delivery are not implemented yet. See the webhook service README for startup.

## Ownership and integration

The webhook service owns subscription and delivery data. The merchant and auth
services currently contain application skeletons only, so the merchant identifier
type and authenticated merchant claim still need agreement with M4/M1. Do not
assume a user ID is a merchant ID or accept a merchant ID from the request body.

Proposed schema: `webhooks`, separate from existing tables in `public`.
Use service-local migrations and a service-local migration history when implemented.
Do not add cross-service foreign keys to another service's tables.

## First table: webhooks.subscriptions

| Field | Proposed PostgreSQL type | Meaning |
| --- | --- | --- |
| id | uuid, primary key | Subscription identifier generated by the service |
| merchant_id | To agree with M4 | Owner identifier derived from authenticated identity |
| callback_url | text, not null | Merchant receiver endpoint |
| event_types | text[], not null | Initially only `parcel.status.changed`; nonempty and validated |
| secret_ciphertext | text, not null | Encrypted signing secret; never returned in list/detail responses |
| is_active | boolean, not null, default true | Whether new events should be sent |
| created_at | timestamptz, not null | Creation timestamp |
| updated_at | timestamptz, not null | Last modification timestamp |

Index `(merchant_id, is_active)` for event processing and merchant-owned lists.
Generate a cryptographically random signing secret server-side and reveal it only
on creation. The webhook sender needs the original secret to calculate HMAC, so
one-way hashing alone is unsuitable. Keep its encryption key outside the database
and repository. Secret rotation is a separate future operation.

## Subscription API proposal

All routes require merchant authentication and server-side ownership checks.

| Method | Route | Result |
| --- | --- | --- |
| POST | /api/v1/merchant/webhooks | Create; return 201 and the signing secret once |
| GET | /api/v1/merchant/webhooks | Paginated list for the authenticated merchant |
| GET | /api/v1/merchant/webhooks/{id} | View an owned subscription without its secret |
| PATCH | /api/v1/merchant/webhooks/{id} | Update callback URL, event types, or active state |

Create input: `callbackUrl`, `eventTypes`. The server sets the owner, ID, secret,
active state, and timestamps. Return 400 for invalid input, 401 for unauthenticated
requests, 403 for a non-merchant role, and 404 for missing or unowned subscriptions.
Disabling a subscription preserves its delivery history.

## Callback validation

Production endpoints require HTTPS and must reject URL credentials, loopback,
private, link-local, and metadata destinations. Validate resolved destinations
when sending as well as when saving; do not follow redirects. Use bounded
connection/read timeouts. Local mock receiver access must be explicitly allowlisted
in a development configuration, not enabled for arbitrary internal addresses.

## Frontend first milestone

Add `WebhookSettings.tsx` under `src/features/merchant/pages` with a subscription
list, add/edit form, and enable/disable action. Display the signing secret once
after creation, with a copy action. Use the shared authenticated API client and
merchant route guard once those integrations are available. Do not hardcode a
merchant identity in production code.

## Subsequent milestones

Delivery records and individual attempts will be separate tables. They will record
event identity, the subscription, payload, delivery status, response code, attempt
number, and timing. Agree the event ID and merchant ID fields with M9 before
implementing deduplication, retries, dead-letter handling, and manual replay.

Before applying the first migration, confirm the merchant ID contract and the
`webhooks` schema with the team. Then implement storage and subscription endpoints,
test ownership isolation, and connect the settings page.
