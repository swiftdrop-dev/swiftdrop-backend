# Parcel Service Cloudinary foundation (Phase 4C.1)

Parcel Service reads `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, and `CLOUDINARY_API_SECRET` from process environment configuration. For local development, set these values in the shell or a local secret manager; do not commit real values or place them in application properties. `.env.example` contains names and placeholders only.

Cloudinary configuration is optional during application startup so unrelated tests and service functions can run without Cloudinary credentials. The first storage operation validates that all three values are present. Missing or partial configuration fails that operation with a sanitized configuration error; values are never included in REST responses or exception messages. The SDK client is constructed lazily after validation.

`DeliveryPhotoStorage` is the provider-independent boundary. The Cloudinary adapter uploads only the `image` resource type as an `authenticated` asset in the fixed `swiftdrop/parcel-delivery-proof` folder. It generates a random UUID public ID, disables overwrite and filename-derived IDs, and does not accept caller-selected transformations, resource types, or folders. Upload results expose only the immutable asset ID, opaque public ID, format, byte size, and resource type. They do not expose URLs or credentials. Deletion uses Cloudinary's immutable asset-ID API and treats `not_found` as already deleted.

## Phase 4C.2 photo-proof core

V4 adds `public.parcel_delivery_photo_proofs`, with UUID proof IDs; parcel, assignment and courier references; Cloudinary asset/public IDs; verified format, content type, byte count, optional SHA-256 digest; and upload, verification, consumption and invalidation timestamps. Foreign keys reference `public.parcels` and a composite key on `public.parcel_assignments`; the composite foreign key enforces that the assignment's parcel and courier match the proof tuple. V4 adds the referenced unique key to V1's assignments table; this is safe for existing rows because `id` is already a primary key. Lifecycle checks disallow consumed-and-invalidated proofs and require all lifecycle times to follow upload, with consumption after verification. A unique asset-ID constraint prevents attaching one Cloudinary asset twice. A partial unique index permits one unconsumed, non-invalidated proof per assignment; it does not depend on the current time. V4 is additive and does not backfill records. It has not been run against a shared database.

The fast test suite uses isolated H2 with Hibernate-generated schema; it does not execute V4. H2 tests exercise application locking, database rollback without physical Cloudinary deletion, and lifecycle checks, but do not prove PostgreSQL migration syntax, composite foreign-key or partial-index behavior, or PostgreSQL row-lock semantics. Validate V4 and the relevant constraints/locking with an isolated PostgreSQL integration environment before deployment.

`DeliveryPhotoValidator` accepts at most 5 MiB, requires the declared MIME type to agree with JPEG/PNG magic bytes, verifies a full decode, and rejects images over 8,000 pixels on either dimension or 12 million total pixels. It calculates a SHA-256 digest of the validated bytes. The storage abstraction receives bounded bytes only after validation. Future request adapters must also enforce the byte cap while reading the request; a service-level byte-array check cannot prevent an upstream component from allocating an oversized body first.

`DeliveryPhotoProofService` is an internal Java service with no HTTP controller. It locks parcel then active assignment, checks the parcel/assignment/courier association, refuses to replace an active proof, validates before uploading, and stores only validated image metadata plus safe Cloudinary identifiers. If upload succeeds but database persistence or transaction commit rolls back, the private Cloudinary asset may remain unreferenced. The service never attempts physical Cloudinary deletion as transaction compensation; cleanup is deferred to a future reconciliation workflow. Asset-ID uniqueness conflicts are still reported without changing or deleting the existing asset. The Cloudinary SDK HTTP5 client is configured with a finite 30-second timeout for connection, pool acquisition and response/read operations; photo uploads hold database locks for the duration of the provider call.

Real reassignment invalidates all unconsumed proof metadata for the previous assignment inside the assignment transaction. Same-courier idempotent assignment does not invalidate proof. Reassignment performs no Cloudinary request; physical deletion is deferred. Consumed proofs are retained. The upload service accepts a courier ID argument only for assignment consistency checking; no trusted courier authentication or identity propagation exists, so this Java service must not be exposed to an untrusted caller until that integration is approved.

No upload HTTP endpoint, photo viewing, notification integration, delivery completion, OTP behavior change, or `in_transit` to `delivered` transition is included. Delivery remains blocked pending OTP/photo consumption design and trusted authentication integration.
